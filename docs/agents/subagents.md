# Built-in subagents

## Built-in subagents
- A child's session file is created in a directory named after its parent, not the flat project directory, so one parent that spawned many workers does not flood the session catalogue. The parent link itself is unchanged (`{ parentSession: parent.sessionFile }` plus the `SUBAGENT_META_TYPE` entry), so child visibility and grouping in the UI are unaffected. See [sessions.md](sessions.md) for the recursive discovery this requires and why `SessionManager.listAll()` is no longer a session-name source.
- **Run status is read from the server, never from the catalogue.** A background run's tool result is written once at dispatch and never revised (completion arrives as a separate transcript message), and a run whose process died keeps a persisted `running`. `lib/subagent-live-status.ts` is one module-level poller, refcounted per session id, that reads `GET /api/subagents/[id]` for watched runs, drops a run from the watch set once the server reports a terminal status, and pauses while the tab is hidden. `subagent-client.ts` holds the fetch; `hooks/useLiveSubagentStatus.ts` exposes it to one row or a set. Every surface showing a status must go through it — the Agents panel (`AgentSessionPanel`), the sidebar family chip (`SessionSidebar`) and the transcript activity row (`SubagentActivity`) — or the three will disagree. `summarizeSubagentStatus` (worst-wins, `lib/subagent-family-status.ts`) collapses a family to the single status its chip shows.
- The Agents panel offers stop and steer for live runs only, over the `POST /api/subagents/[id]` actions that already existed unused. A row's stop is awaited so a run that settles between render and click reports instead of raising an unhandled rejection; stop-all uses `Promise.allSettled` so one failure cannot strand the rest. The row hosts those controls as siblings of its select button, so the panel is `role="group"` with `aria-current` — a `listbox` may only contain options, and the steer input is not one.
- `getRecentProjects` and `getProjectActivity` (`lib/project-groups.ts`) skip sub-agent sessions: a child belongs to its parent's conversation, not to a project, and a worktree-isolated child contributed an entry for a temporary worktree directory that is deleted when the run ends. `sessionsForProject` deliberately still returns children, because family grouping needs them to attach to the parent's row.
- A child that carries no `parentSession` header is linked to its parent by location instead (`lib/nested-session-parent.ts`): children live under a folder named after the parent session, either by its file stem or by its id. The search walks **up** to the nearest such ancestor, because depth is not uniform — pi-web writes a child straight into the parent's folder, while `nicobailon/pi-subagents` writes `<parent folder>/<child run id>/run-0/session.jsonl`. Nearest match wins, so a grandchild joins its own parent rather than the outermost one. Such a child becomes a **sub-agent**, not a fork, so family grouping hides it from the top-level list. Two guards: a header link always wins, and a child whose parent cannot be resolved stays a fork, because family grouping drops a child with no reachable parent and it would otherwise become unreachable in the UI.
- The sidebar family row carries the only sign a session has children: `SessionItem`'s `subagentCount` / `subagentStatus` chip. (The earlier `hasChildren` / `collapsed` / `onToggleCollapse` props were dead — the only `<SessionItem>` call site never passed them.) Clicking it selects the family and opens the Agents panel with open, not toggle, semantics so switching families does not close it.
- A sub-agent tool call renders as `SubagentActivity` instead of the generic tool card: a fan-out of a dozen workers would otherwise bury the conversation that asked for it. Status leads; the task (read from the tool input, since older runs have none in `details`), the worktree and the error appear on expand, along with the tool result text — for `get_subagent_result` that text is the whole point of the call. Only a live status falls back to the clock for its duration; a settled run without `completedAt` shows no duration rather than one measured in months.
- **Runs owned by another extension** are read from the files that extension persists. `nicobailon/pi-subagents` writes `<PI_SUBAGENTS_TEMP_ROOT or os.tmpdir()/pi-subagents-uid-<uid>>/async-subagent-runs/<runId>/status.json`, and its maintainers document file reading as the supported path for an out-of-process host — its RPC is in-process only (`pi.events` never reaches another process), so there is nothing to call. `lib/external-subagent-status.ts` reads them; `GET /api/subagents/external` exposes it. Four rules from that documentation are load-bearing: only `queued`/`running` are live; `paused` is an interrupt and `stopped` a deliberate stop; **mtime and `lastUpdate` are not a heartbeat** (the runner only rewrites the file when the activity classification changes), so liveness comes from `process.kill(pid, 0)`; and `sessionId` must be matched against both a path and a bare id. State maps `complete`->`completed`, `partial`->`failed` (terminal, no partial bucket), `paused`->`interrupted`, `stopped`/`rejected`->`aborted`, and a missing state -> `starting`, covering the window before the first write.
- A background run's **completion** is a separate transcript entry, not a tool result: the other extension posts a `custom` message with `customType: "subagent-notify"` and `details: SubagentNotifyDetails[]` (agent, status, taskInfo, resultPreview, durationMs, childRuns, watchdogBlockers). Because a background tool result is written once at dispatch, that notice is the only place the finished outcome appears, so pi-web renders it as a grouped completion card rather than the raw text blob it used to show. The four notice states are settled only — `paused` is an interrupt, `stopped` a stop — and map like run states do. Dispatch happens in a thin `CustomMessageView` wrapper so the generic card's hooks stay unconditional.
 The run directory is **never enumerated**: it grows without bound and is reaped underneath us by atomic rename, so every read tolerates ENOENT. The poller asks only for the runs that extension currently marks live (`.active-runs/`), and run ids are pattern-checked before any path join.
- `lib/subagent-tool-adapter.ts` maps **any** runtime's tool result to one `SubagentRunView`, which is what `SubagentActivity` renders, so the two cannot drift apart. pi-web's own `pi-web-subagent` details map to a single run; `nicobailon/pi-subagents` reports a `results` array under its own `subagent` tool name, and each row becomes its own transcript row — a fan-out is one tool call with many children. That runtime has no status field, so state is derived from `exitCode` / `stopped` / `interrupted` / `timedOut`; a `results` row only exists once the child settled, so a mapped run is never live. Detection returns null for anything else, which is what keeps every other tool call on the generic card.
- Sub-agents are shown in a **dock**, not a dropdown: `SubagentDock` is a peer tab of the file and terminal tabs in the dock panel, so it keeps its state while another tab is active and never covers the conversation. The top-bar Agents button and the sidebar family chip both open it (`openAgentsDock`), and the chip's callback names the family root so switching families switches the dock rather than toggling it. The dropdown that used to hang off the top bar is gone: one surface, not two.
- A sub-agent that ran in a temporary isolation worktree leaves a cwd that no longer exists once the run ends, and other runtimes do not name that worktree the way `inferRemovedWorktree` recognises. `attachSessionProjectInfo` therefore lets such a session inherit its **parent's** project, which is where the work actually happened. Without it a finished run appears as its own broken project in the picker.
- The global `builtInEnabled` in `~/.pi/agent/agents/settings.json` is off when the file or field is absent and when the file is malformed (fail closed); writes are atomic and keep unknown fields. The inline extension factory is always present, so a reload can apply the switch, but registers no tools while off; after changing it the user must reload the session explicitly, and `Agent` dispatch re-checks the setting so a stale call cannot start a subagent. When on, only a recognized legacy `pi-subagents` extension registering a reserved tool (`Agent`, `get_subagent_result`, `steer_subagent`) is removed, along with the conflict errors it caused; unrelated extensions stay. ADR 0003.
- The three tools register with `exposure: "model-only"`, so `ctx.executeTool()` (a codemode script) cannot start, collect or steer a subagent: a script-started run would record the nested call id (`<codemode call>/<n>`) as its `parentToolCallId`, which no transcript entry carries, and the chat would lose its link to the child session. `lib/subagent-extension.integration.test.mjs` pins this against a real `AgentSession`.
- A run stays in `getSubagentRuns()` from dispatch until its result entry is written, so `get()` reports a persisted `running` / `queued` status with no result and no running wrapper as `interrupted`: its process stopped and nothing will finish it (otherwise `get_subagent_result({ wait: true })` polls forever after a restart).
- Built-in profiles (`general-purpose`, `explore`, `plan`) are switched off by name in that file's `disabledBuiltIns`, never by copying them to a `.md` file (ADR 0005). `builtInProfiles()` stamps `enabled` onto them so the panel, the `Agent` tool description and `resolveSubagentProfile` agree. Writes are minimal edits that keep names they did not touch, including ones no built-in claims; reading fails *open* (the feature switch has already failed closed). `PATCH /api/subagents/profiles` with `scope: "builtin"` writes it; `PUT`/`DELETE` refuse that scope. A same-name file replaces the built-in outright and is switched off through its own frontmatter. Only the switch is live for a built-in; the rest of the form is read-only.
- `notifyParent` skips a background run's completion notification when the parent already collected that result with `get_subagent_result`, which marks it consumed. The mark names the run (`sessionId` + `completedAt`), never just the session, since `resume` reuses the session id; `resume` keeps the mark. While the parent `isRunning()` (often still inside that poll) the notification is held and the mark re-checked; an idle parent is notified at once.
- The notification is a `custom` message, which pi's `convertToLlm` replays as a plain `user` turn, so `subagentNotificationText()` prefixes `SUBAGENT_NOTIFICATION_PREFIX`; otherwise compaction files the report under the user's Goal / Constraints. Keep the prefix in code, never in a profile prompt, so the model cannot drop it. A `resume`d run's notification adds a line saying it supersedes the earlier report, which it would otherwise repeat word for word. Foreground `Agent` and `get_subagent_result` results are `toolResult`s and keep the bare `subagentFinalText()`.
- Profile files (`~/.pi/agent/agents/*.md`, project `.pi/agents/*.md`) are shared with other runtimes: a save round-trips every frontmatter key outside `MANAGED_FRONTMATTER_KEYS` (`lib/subagents.ts`; e.g. `name`, `allowed_subagents`, `exclude_extensions`, `disallowed_tools`) and carries foreign `ext:` tool selectors through. The pi-subagents aliases `skills` / `extensions` are seeded on first save and kept in step with `load_skills` / `load_extensions` while they hold a boolean (or `none` / `all`); a whitelist such as `extensions: pi-advisor-flow` is never rewritten, and the flags fall back to the aliases when `load_skills` / `load_extensions` are absent.
